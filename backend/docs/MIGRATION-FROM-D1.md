# D1 → PostgreSQL 데이터 이전

이 문서의 절차는 **Cloudflare 계정이나 운영 DB에 접속하지 않습니다.** 내보낸 CSV/JSON 파일만 입력으로
받아 검토 가능한 SQL을 생성하고, 그것을 PostgreSQL에 적용합니다.

이전 대상은 두 개뿐입니다.

| D1 (SQLite) | PostgreSQL | 변경점 |
| --- | --- | --- |
| `removed_members(person_id TEXT PK, removed_at TEXT)` | `removed_members(person_id text PK, removed_at timestamptz)` | 시각을 실제 타임스탬프 타입으로 |
| `task_reschedules(id INTEGER PK AUTOINCREMENT, ...)` | `task_reschedules(id bigint GENERATED BY DEFAULT AS IDENTITY, ...)` | identity 방식, id 보존 가능 |

## 1단계 — D1에서 내보내기

운영 담당자가 수행합니다. 두 방법 중 편한 쪽을 쓰세요.

```bash
# JSON (권장) — wrangler가 { "results": [...] } 형태로 내보냅니다.
wrangler d1 execute <DB_NAME> --remote --json \
  --command "SELECT person_id, removed_at FROM removed_members" > removed_members.json

wrangler d1 execute <DB_NAME> --remote --json \
  --command "SELECT id, task_key, person_id, task_title, from_start, to_start, reason, changed_by, changed_at FROM task_reschedules ORDER BY id" > task_reschedules.json
```

CSV도 지원합니다. 첫 줄이 D1 컬럼명 헤더이고 RFC 4180 따옴표 규칙을 따르면 됩니다.

> `task_reschedules`는 **`id`를 반드시 포함해서** 내보내세요. id 순서가 "가장 최근 변경값"의 의미를
> 결정하므로, 순서를 잃으면 일정 이력이 잘못 해석됩니다.

## 2단계 — SQL 생성

```bash
# 저장소 루트에서
mkdir -p backend/tools/out
node backend/tools/import-d1.mjs \
  --removed-members  ./removed_members.json \
  --task-reschedules ./task_reschedules.json \
  --out backend/tools/out/import.sql
```

생성기가 하는 일:

- 컬럼별 타입 검증(정수/타임스탬프/NOT NULL). 어긋나면 **행 번호와 함께 실패**하고 아무것도 만들지 않습니다.
- 작은따옴표 이스케이프. 한국어 본문과 쉼표가 포함된 사유도 안전합니다.
- `removed_members`는 `ON CONFLICT (person_id) DO UPDATE`, `task_reschedules`는 `ON CONFLICT (id) DO NOTHING`.
  → **여러 번 실행해도 안전합니다.**
- 마지막에 identity 시퀀스를 `MAX(id) + 1`로 재설정합니다.

생성된 SQL은 평문이므로 적용 전에 반드시 눈으로 확인하세요.

## 3단계 — 스키마 준비

Flyway가 애플리케이션 기동 시 자동으로 적용합니다.

```bash
cd backend
docker compose up -d
./gradlew bootRun     # V1, V2 마이그레이션이 여기서 적용됨
```

## 4단계 — 적용

```bash
psql "postgresql://handover:handover@localhost:5432/handover" \
  -v ON_ERROR_STOP=1 \
  -f backend/tools/out/import.sql
```

전체가 하나의 `BEGIN; ... COMMIT;` 트랜잭션입니다. 중간에 실패하면 아무것도 남지 않습니다.

## 5단계 — 검증

```sql
-- 건수 비교 (D1 쪽 SELECT count(*) 결과와 대조)
SELECT count(*) FROM removed_members;
SELECT count(*) FROM task_reschedules;

-- 이전된 최대 id 확인
SELECT max(id) FROM task_reschedules;

-- 업무별 "현재 시작 주" — 화면에 보이는 값과 대조
SELECT DISTINCT ON (task_key) task_key, to_start, changed_at
FROM task_reschedules ORDER BY task_key, id DESC;
```

시퀀스는 쿼리로 보는 것보다 **실제로 한 건 넣어 보는 편이 확실합니다.**
(`pg_sequences.last_value`는 시퀀스를 아직 읽지 않았으면 NULL이라 판단에 쓸 수 없습니다.)
새로 만들어진 행의 id가 위 `max(id)`보다 크면 정상입니다.

API로도 확인합니다.

```bash
curl -s localhost:8080/api/schedules \
  -H 'oai-authenticated-user-id: check' \
  -H 'oai-authenticated-user-email: <등록된 이메일>' | jq '.changes | length'
```

## 검증 기록

이 저장소의 로컬 D1(miniflare)에 있던 실제 데이터로 전 과정을 실행했습니다.

- `task_reschedules` 4건, `removed_members` 0건을 `sqlite3 -json`으로 내보냄
- 생성된 SQL을 적용 → **id 2, 7, 8, 9가 그대로 보존됨** (D1에서도 비연속이었음)
- 같은 SQL을 한 번 더 적용 → 4건 모두 무시되고 중복 없음
- 이전 직후 API로 신규 일정 변경을 기록 → **id 10 부여, 충돌 없음**
- `GET /api/schedules`의 `changedAt`이 D1 시절 문자열과 동일
  (예: `2026-08-27T14:38:48.058Z`)

`sqlite3 -json`은 **0건일 때 빈 파일**을 만듭니다. 이전 도구는 이 경우를 0행으로 처리합니다.

## 시각 값에 대해

D1은 `new Date().toISOString()`이 만든 ISO-8601 문자열을 TEXT로 저장했습니다. 이전 도구는 이를 파싱해
`timestamptz`로 넣고, 백엔드는 응답할 때 다시 **같은 형식(UTC, 밀리초 3자리, `Z`)** 으로 직렬화합니다.
따라서 프론트가 받는 `changedAt` 문자열은 이전과 동일합니다.

## 롤백

기존 Next.js + D1 백엔드는 그대로 살아 있습니다. Spring 백엔드를 내리고 프론트의
`NEXT_PUBLIC_API_BASE_URL`을 비우면 즉시 원래 동작으로 돌아갑니다. 이전 작업은 D1을 읽기만 하므로
원본 데이터는 변경되지 않습니다.
